# Инфраструктурная DoS-защита SmartPlate

Дата проверки: 2026-06-27.

## Найдено до усиления

- nginx не содержал `limit_req`, `limit_conn` и явного
  `client_max_body_size`;
- Fastify слушал `0.0.0.0:3000`, хотя nginx обращается к нему через localhost;
- UFW уже был активен: incoming deny-by-default, разрешены только
  `22/tcp`, `80/tcp`, `443/tcp`;
- PostgreSQL слушал только `127.0.0.1:5432` и `[::1]:5432`;
- порт Node 3000 и Zabbix 10050 были видны в `ss`, но блокировались UFW;
- PM2 запускал один `smartplate-api` в `fork_mode`. Распределённый Redis
  rate-limit при такой конфигурации не нужен.

## Применяемая защита nginx

| Поверхность | Постоянная скорость | Допустимый burst |
|---|---:|---:|
| остальные API | 20 запросов/сек на IP | 40 |
| `/auth/` | 60 запросов/мин на IP | 60 |
| `/subscription/payment` | 20 запросов/мин на IP | 20 |
| `/feedback` и ответы | 60 запросов/мин на IP | 30 |
| `/admin` | 10 запросов/сек на IP | 40 |

Дополнительно: максимум 30 одновременных соединений с одного IP, nginx
возвращает 429 при превышении. Лимиты намеренно не заменяют более строгие
Fastify-лимиты отдельных действий и оставляют запас семьям, офисам и
нескольким вкладкам за одним NAT.

`client_max_body_size 8m` совпадает с Fastify `bodyLimit`. Это сохраняет
легитимный payment screenshot (до 5 MiB исходного файла / около 7 MiB base64),
но не позволяет отправлять в Node произвольно большие тела. Node теперь по
умолчанию слушает только `127.0.0.1`; внешний bind возможен лишь явным `HOST`.

Файлы для production:

- `server/nginx/smartplate-ratelimits.conf` → `/etc/nginx/conf.d/`;
- `server/nginx/smartplate-api-proxy.conf` → `/etc/nginx/snippets/`;
- `server/nginx/api.voronova.online` → `/etc/nginx/sites-available/`.

После копирования обязательны `nginx -t` и только затем `systemctl reload nginx`.

## Firewall и порты

Разрешённые UFW-порты соответствуют сценарию: SSH и nginx. PostgreSQL не
публикуется. После backend deploy порт 3000 должен отображаться только как
`127.0.0.1:3000`.

Zabbix agent слушает `0.0.0.0:10050`, но UFW его не разрешает. Его bind не
менялся, потому что это инфраструктура хостинг-провайдера; перед изменением
нужно подтвердить способ связи агента с серверами `92.53.116.12/111/119`.

## Бэкапы и восстановление

- cron: ежедневно в 03:00;
- локально хранятся три последних GPG-файла;
- B2 хранит зашифрованные копии 30 дней;
- секреты `.gpg-passphrase` и `.b2-credentials` имеют права 600;
- мониторинг считает бэкап просроченным после 26 часов.

27 июня выполнен полный restore-drill последнего файла
`smartplate_db_2026-06-27_03-00.sql.gz.gpg` в одноразовую БД. Расшифровка,
`gunzip`, импорт с `ON_ERROR_STOP`, запрос к `recipes` и автоматическая очистка
прошли успешно. Тот же файл подтверждён в B2.

Restore-drill следует повторять ежемесячно и после изменения `backup.sh`.

## Когда нужен Redis

Текущий PM2 — один процесс, поэтому in-memory Fastify rate-limit согласован.
До перехода на `cluster_mode`, нескольких PM2 instances или нескольких VPS
нужно подключить Redis store; иначе каждый процесс получит отдельный счётчик и
эффективный лимит умножится на число процессов.
