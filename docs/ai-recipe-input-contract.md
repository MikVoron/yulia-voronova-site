# Контракт «Text → Recipe»

Единый источник правды о том, как AI (Claude Code) превращает **свободный русский текст рецепта** в структуру данных проекта. Это **постоянный контракт**, а не разовый кейс: пользователь присылает текст — AI сам распознаёт, валидирует и выдаёт SQL-миграцию `INSERT INTO recipes (...)` или JSON по контракту ниже.

## 0. Режим данных: `strict` (No Guessing) — по умолчанию

**Дефолтный режим работы: `strict`.** Альтернатива — `assist` — включается **только** явной фразой пользователя («включи assist», «разреши угадывать», «заполни по здравому смыслу»). Без такого триггера — всегда `strict`.

### Обязательные правила

1. AI извлекает **только** те данные, которые **явно есть во входном тексте**.
2. AI **не придумывает** и не «дозаполняет» поля по контексту, привычке или вероятности. Никаких «взял из предыдущей версии», «по аналогии», «разумного дефолта».
3. Если данных не хватает / значение неоднозначно / есть конфликт:
   - поле → `null` (или пустое значение по контракту: `[]` для массивов, опущенное поле у объекта шага/ингредиента);
   - добавить запись в `_needs_clarification` с **коротким конкретным вопросом**.
4. Любые предположения запрещены, пока пользователь явно не включит `assist`.
5. Ошибка/неясность в одном поле **не ломает** обработку всего рецепта — см. §4.

**Нюанс:** косвенный вывод из явного маркера в тексте — **не** guessing. Пример: текст «Раздел: основные блюда» → `cat=mains`. Такие случаи идут в `_filled_from_input` с пометкой `inferred: <основание>`.

**Исключение:** жёсткие дефолты контракта (`is_free=false`, `is_published=false`, `sort_order=0`, 4 пустых `add_*`) — ставятся молча, в отчёт не попадают.

### Обязательные служебные поля в выдаче

Каждый раз AI **обязан** вернуть рядом с SQL/JSON три списка:

- **`_filled_from_input`** — поля, заполненные напрямую из текста (пары `поле → значение [+ inferred: основание]`).
- **`_needs_clarification`** — поля, требующие уточнения, **с коротким вопросом**.
- **`_not_provided`** — поля, которых во входе нет и вопроса не требует (`vk_video`, `yt_video`, `note` и т.п.).

### Примеры поведения

| Ситуация | ❌ Нельзя | ✅ Правильно |
|---|---|---|
| `emoji` не указан | поставить `🥣` «по смыслу» | `emoji: null` + `_needs_clarification: "emoji не указан — какой поставить?"` |
| «1 цельнозерновой хлеб» без единицы измерения | `amount: "1 шт."` | `amount: null` + `_needs_clarification: "хлеб: вес/ломтик/штука?"` |
| `time_min` не указан | «борщ обычно 45 мин» | `time_min: null` + вопрос |
| КБЖУ не указан | рассчитать по ингредиентам | все поля `null` + один вопрос «КБЖУ рассчитать или пропустить?» |
| «Раздел: основные блюда» | — | `cat: "mains"` (прямое сопоставление, в `_filled_from_input`) |
| «сложность: средняя» | — | `difficulty: "medium"` |

### `steps[i].photo` — строго только контракт

Независимо от режима: `string` / `string[]` / `true` / `null`. Никаких других форм. Подробности — §2.3 и §2.5.

## 1. Вход

Свободный текст на русском: произвольный формат, обычно содержит:
- название, эмодзи (опц.);
- КБЖУ, вес порции, порции, время, сложность (опц.);
- список ингредиентов (часто «Продукт — N г», «чем заменить: ...»);
- пронумерованные или абзацные шаги;
- указания на фото («фото шага 3», «2 фото на 10-м шаге», «фото будет позже»);
- цитату автора и/или заметку (опц.);
- add-блоки («к этому подходит: мясо 50 г — 80 ккал / 16 / 1 / 0 / 0»).

AI **ничего не просит в формате JSON**: парсит всё сам. Если поле не определяется — оставляет `null` / опускает по контракту ниже. Никогда не выдумывает КБЖУ, граммовку, время и т.п.

## 2. Выход (структура рецепта)

Серверная схема БД (таблица `recipes`). Все имена полей — **snake_case**.

### 2.1 Корневые поля

| Поле | Тип | Правило |
|---|---|---|
| `id` | string | kebab-case slug, напр. `borscht-red-beans`. Если не дан — вывести из названия. |
| `cat` | string | Одна из `breakfasts`, `mains`, `pancakes`, `spreads`, `sauces`, `salads`, `drinks`. По смыслу блюда. `spreads` — намазки (хумус, паштет), `sauces` — соусы и заправки. |
| `name` | string | Обязательно. |
| `emoji` | string \| null | Один emoji. |
| `time_min` | int \| null | Целое число минут — **нижняя граница** диапазона (для фильтров и сортировки). «45–50 мин» → `45`. «1–1,5 часа» → `60`. Не округлять и не усреднять. То же — `servings`, `portion_grams`. |
| `time_label` | string \| null | **Дословно** строка времени из исходного текста, как пользователь её дал: `"45–50 минут"`, `"1 час 20 минут"`, `"около 30 минут"`. **Эта строка показывается на карточке.** Если в тексте указано одиночное значение (напр. «30 минут») — `time_label = null`, фронт сам соберёт `"30 мин"` из `time_min`. |
| `difficulty` | enum | Только `easy` / `medium` / `hard`. |
| `servings` | int \| null | Порций. |
| `portion_grams` | int \| null | Грамм в одной порции. |
| `is_free` | bool | `true` = триал, `false` = Pro. По умолчанию `false`, если пользователь не сказал. |
| `kcal`, `protein`, `fat`, `carbs`, `fiber` | int \| null | КБЖУ на порцию. Только явные цифры. |
| `tags` | string[] | PostgreSQL `TEXT[]`, напр. `ARRAY['без глютена', 'растительное']`. |
| `photo` | string | Cover: `images/recipes/{slug}/{slug}-cover.webp` или `-final.webp` (если cover == final). |
| `quote` | string \| null | Цитата автора в полном виде. Не сокращать. |
| `note` | string \| null | Заметка/совет. |
| `vk_video`, `yt_video`, `dzen_video` | string \| null | Ссылки на видео. `null` если нет. |
| `sort_order` | int | `0` если не указан — пометить в выдаче, что нужно назначить вручную. |
| `is_published` | bool | Обычно `false` на старте, пользователь потом публикует. |
| `added` | — | **НЕ указывать вручную** — берётся из `created_at` БД. |

### 2.1.1 Правило именования новых `id`

Для **новых** рецептов выбирать `id` так, чтобы по нему сразу читался тип блюда. Рекомендуемые префиксы:

- супы: `soup-*`;
- салаты: `salad-*`;
- котлеты / тефтели / биточки: `cutlets-*`;
- гарниры: `side-*`;
- соусы: `sauce-*`;
- намазки: `spread-*`, если это помогает отличить рецепт от соуса.

Папка и файлы фото должны повторять выбранный `id`: `images/recipes/{id}/{id}-cover.webp`, `{id}-N.webp` и т.д.

**Существующие опубликованные `id` не переименовывать автоматически.** Если старый `id` уже используется в БД, ссылках, add-ons, избранном или заметках, переименование — это отдельная миграция с проверкой всех ссылок и production DB.

### 2.2 `ingredients`: массив `{ name, swap }`

```json
[
  {"name": "Свёкла — 3 средние (запечённая или отварная)", "swap": null},
  {"name": "Томатная паста — 2 ст. л.", "swap": "Томаты в собственном соку — 200 г"},
  {"name": "овощной концентрат — 1 ч. л.", "swap": "Можно без него"}
]
```

Правила:
- `name` — **непустая строка**, продукт + количество/граммовка в одной строке;
- `swap` — строка (замена/альтернатива) **или** `null`;
- если в тексте «(можно без него)» → перенести в `swap: "Можно без него"` (канонический регистр), из `name` убрать;
- если ингредиент ссылается на другой рецепт — оформить как `[текст](recipeId)` в `name` или `swap` (см. `feedback_ingredient_links.md`);
- ничего, кроме `name` и `swap`, в объект ингредиента не класть.

### 2.3 `steps`: массив `{ text, photo }`

```json
[
  {"text": "Лук мелко нарежьте..."},
  {"text": "Добавьте чеснок и лимонный сок.", "photo": ["images/recipes/borscht-red-beans/borsch-10.1.webp", "images/recipes/borscht-red-beans/borsch-10.2.webp"]}
]
```

Правила:
- `text` — непустая строка;
- `photo` — строго один из: `string` / `string[]` / `true` / `null` (поле можно опустить = `null`);
- **несколько фото на шаге всегда массив строк** (не одна строка через запятую);
- **не** вставлять start/final фото в шаги — фронтенд рендерит их автоматически из cover-пути (`-start.webp` перед первым шагом, `-final.webp` в финальный автошаг);
- если в тексте «фото будет позже» / «плейсхолдер» → `photo: true`;
- если фото не упомянуто → поле опустить (эквивалент `null`).

### 2.4 `add_protein`, `add_fat`, `add_carbs`, `add_fiber`

Всегда возвращаем **все 4 массива**, даже пустые (`[]`). Пустые = нет сайдбара.

Формат элемента: `{name, amount, kcal, protein, fat, carbs, fiber, recipeId?}`. `recipeId` — опционально, если add-ингредиент это отдельный рецепт в БД.

### 2.5 Фото (пути и маппинг на шаги)

Только относительные пути от корня репозитория, по шаблону `images/recipes/{slug}/{slug}-*.webp`.

**Семантика суффиксов — ЖЁСТКАЯ (AI обязан следовать):**

| Файл | Куда попадает | Как |
|---|---|---|
| `{slug}-cover.webp` | Обложка рецепта | Поле `photo` у корня (ставит автор миграции) |
| `{slug}-start.webp` | Автоблок «стартовое фото» перед первым шагом | Рендерит **фронтенд** автоматически из cover-пути. В `steps` **не вставлять**. |
| `{slug}-final.webp` | Автошаг «Наслаждайтесь! Приятного вам аппетита 😋» | Рендерит **фронтенд** автоматически. В `steps` **не вставлять**. |
| `{slug}-N.webp` | Шаг N (1-индексация) | `steps[N-1].photo = "images/recipes/{slug}/{slug}-N.webp"` |
| `{slug}-N.1.webp`, `{slug}-N.2.webp`, … | Шаг N, мультифото | `steps[N-1].photo = [".../{slug}-N.1.webp", ".../{slug}-N.2.webp", …]` |

**Критическое правило при парсинге:** AI **обязан перечислить все файлы** в `images/recipes/{slug}/` и **разложить их по шагам автоматически** по правилу `{slug}-N.webp → steps[N-1].photo`. Пропуски нормальны: если `{slug}-3.webp` нет — `steps[2].photo` опускается. Не оставлять 90% шагов без фото, если файлы в репо есть.

Никаких CDN, абсолютных URL или выдуманных путей. Если имён файлов нет в репо — использовать шаблон, но в `_todo` отчёта пометить: «положить `{slug}-N.webp` для шагов X, Y, Z».

## 3. Правила распознавания

| Из текста | В структуру |
|---|---|
| `Свёкла — 300 г` | `{"name": "Свёкла — 300 г", "swap": null}` |
| `Томатная паста 2 ст. л. (можно без него)` | `{"name": "Томатная паста — 2 ст. л.", "swap": "Можно без него"}` |
| `чем заменить: Петрушка` / `или: Петрушка` | переносим в `swap: "Петрушка"` последнего ингредиента |
| Нумерованный список / абзацы | → `steps[]` по порядку |
| «фото шагов 3 и 5» | `steps[2].photo` и `steps[4].photo` заполняются строкой-путём |
| «на шаге 10 — два фото» | `steps[9].photo: ["...-10.1.webp", "...-10.2.webp"]` |
| Файл `{slug}-N.webp` лежит в папке рецепта | `steps[N-1].photo` заполнить автоматически, **без напоминания** от пользователя |
| «фото будет позже» / «плейсхолдер» | `photo: true` |
| фото не упомянуто | поле `photo` опускаем |
| КБЖУ указан «на порцию» — берём как есть; «на 100 г» — пересчитываем **только** если явно дано `portion_grams` | |

Важно: **не выдумывать** КБЖУ и граммы. Если нет — `null`. Если пользователь прислал «~400 г» / «около» — берём число, в `note` не дублируем.

## 4. Валидация перед сохранением

AI **обязан** проверить результат перед отдачей пользователю:

1. `ingredients[].name` — непустая строка; иначе элемент отбросить, отметить в отчёте.
2. `ingredients[].swap` — строка или `null`; любое другое значение → `null`.
3. `steps[].text` — непустая строка; пустой шаг отбросить.
4. `steps[].photo` — только `string` / `string[]` / `true` / `null`. Иначе → `null`.
5. Если `photo` — массив: отфильтровать пустые/битые строки; если после фильтрации пусто → `null`.
6. `difficulty` ∈ `{easy, medium, hard}`; иначе → `null` + пометка в отчёте.
7. `cat` ∈ списке допустимых категорий; иначе → в отчёт как «нужна вручную».
8. Числовые поля (`time_min`, `kcal`, `protein`, `fat`, `carbs`, `fiber`, `servings`, `portion_grams`) — целые; нечисло → `null`.
9. `tags` — массив строк; пустой допустим.

Принцип: **ошибка в одном поле не должна валить весь импорт**. AI логирует проблему в финальный отчёт («что не смог определить») и продолжает формировать структуру.

## 5. Формат выдачи

По умолчанию AI отдаёт **SQL-миграцию** в `server/migrate-recipe-{slug}.sql` в стиле `server/migrate-borsch.sql`:
- `INSERT INTO recipes (...) VALUES (...) ON CONFLICT (id) DO UPDATE SET ...`;
- `ingredients`/`steps`/`add_*` — как `'[...]'::jsonb`;
- `tags` — как `ARRAY[...]`;
- в шапке — комментарий с командой применения на VPS.

Если пользователь просит чистый JSON — отдать JSON по той же структуре, без SQL-обёртки.

## 6. Финальный чек-лист для AI

После каждого парсинга AI в ответе пользователю:

1. ✅ **Принял текст** — указал, что распарсил.
2. ✅ **Распарсил** — собрал структуру по контракту §2 **в режиме `strict`** (§0): без выдумок и скрытых допущений.
3. ✅ **Провалидировал** — применил §4, ничего не валится на одном битом поле.
4. ✅ **Выдал структуру** (SQL-миграцию по умолчанию) + **обязательный отчёт** из трёх списков:
   - `_filled_from_input` — что извлечено из текста (с пометкой `inferred: <основание>`, если вывод косвенный);
   - `_needs_clarification` — чего не хватило, **с конкретным вопросом**;
   - `_not_provided` — что отсутствует и вопроса не требует.
   - Дополнительно (опционально): `_warnings` (что отбросил при валидации и почему), `_todo` (фото-файлы, ручные действия).
