# План безопасности и надёжности SmartPlate

Статус: обновлён 2026-09-11. Это рабочая последовательность: один крупный этап
за раз, с checkpoint, проверкой и понятным откатом. Она не заменяет продуктовый
план и не требует изменений дизайна.

## Выполнено

- SSH-доступ root отключён; рабочий доступ — `smartplate-admin` по ключу и с
  парольным `sudo`. Аварийный доступ остаётся через консоль Timeweb.
- API-процесс `smartplate-api` работает от UID/GID `997`, без Linux capabilities.
  PM2-менеджер пока остаётся root, но больше не является пользователем самого API.
- Проверены локальный зашифрованный backup БД, cron и мониторинг; перед рискованными
  изменениями созданы root-only checkpoints с архивом файлов и custom DB dump.
- Обновлены production-зависимости: Fastify `5.12.3`, Nodemailer `9.1.1`,
  fast-uri `3.1.6`, find-my-way `9.9.0`; `npm audit --omit=dev` = 0.
- После обновления проверены local/public `/health`, PM2, UID/GID `997` и отсутствие
  активного rollback timer.
- Для закрытых рецептов API уже не выдаёт гостю ingredients, steps и note;
  приватные API-маршруты возвращают 401 без сессии.
- CSP для script выполнен: inline scripts и inline event handlers удалены. Переход
  от inline styles — отдельная, не срочная задача.

Прототип не выполняет deploy. Старый временный helper не становится универсальным
после переноса файлов. Пункт 1 целиком пока не завершён.

Ближайший малый шаг: выполнить через Timeweb подготовленный root PM2/systemd-прогон
с control-envelope, затем проверить результат, cleanup и неизменность production.
Он должен проверить timer rollback и обрывы под общим flock на искусственных
процессах UID997. Boot recovery и все проверки реального приложения — последующие
обязательные этапы до допуска к production. Рабочий PM2_HOME не использовать.

Локальная политика boot/clock recovery исправлена после проверки:
`server/ops/release/recovery-policy.cjs` явно возобновляет `rolling_back`,
привязывает запись схемы 2 к релизу/manifest и проверяет оба десятиминутных окна.
Перевод часов назад больше не блокирует цепочку rollback → restored → cleanup;
нормализация времени разрешена только этим операциям. Проверки времени для
подтверждения не ослаблены. Recovery-тесты: 16/16, общий Windows-прогон
с PM2 contract-тестами: 41 passed, 7 Linux-only skipped; на VPS 48/48.
Unit-тесты не запускают PM2/API; отдельный PM2-прогон описан выше.
Единая запись state/recovery и отмена незавершённого arming проверены 2026-09-11
в отдельном файловом стенде: новые тесты VPS 18/18, общий локальный набор 52 passed,
14 Linux-only skipped. Прикладное evidence в этом стенде модельное. Подключение
журнала к root-owned хранилищу, реальным таймерам, PM2 и UID997 реализовано в новом
fixture-стенде, но ещё ожидает привилегированного прогона. Интегрированная boot/PM2-
репетиция не подтверждена. Пункт 1 остаётся открытым.

Сделать:

1. Переписать `docs/smartplate-release-checklist.md` под `smartplate-admin`,
   парольный `sudo`, `PM2_HOME=/root/.pm2` и API от UID 997.
2. Вынести проверенный release/rollback helper из временной папки в поддерживаемое
   место с версией и тестом синтаксиса.
3. Перед каждым API-релизом: checkpoint, сборка зависимостей отдельно от live с
   читаемыми для UID 997 правами, проверка их загрузки и тесты, timer rollback,
   local/public health, затем явное confirm. Откат возвращает сохранённые модули
   с прежними правами без повторного `npm ci` и без зависимости от сети.

Критерий готовности: следующий малый API-релиз проходит по документу без ручных
команд root и без временных сценариев.

## Приоритет 2 — сделать в ближайшие 1–2 недели

### 2. Реальная проверка восстановления backup

Сейчас подтверждены расшифровка и структура локального encrypted dump, а также
есть свежие checkpoints. Нужен отдельный restore-drill в одноразовую БД и проверка
скачивания одного зашифрованного файла из Backblaze B2.

Критерий готовности: без обращения к production DB восстановлены данные в
одноразовую БД, проверены таблицы и удалена тестовая БД. Повторять ежемесячно и
после изменения backup-скрипта.

### 3. Решение по видео закрытых рецептов

Известный риск: прямые URL видео у части закрытых рецептов могут быть удобны для
пересылки вне подписки. Это вопрос бизнес-правила, а не косметическая правка.

Сначала выбрать политику:

- видео можно свободно смотреть и оно служит анонсом рецепта; или
- видео — часть платного контента.

Если видео платное: отдельный этап с авторизованной выдачей/подписанными URL,
проверкой доступа и тестами гостя, trial и paid-пользователя.

## Приоритет 3 — после этого, без срочности

### 4. Внешний мониторинг

Локальный мониторинг полезен, но не видит часть сетевых сбоев. Добавить внешнюю
HTTP(S)-проверку `plate.voronova.online` и `api.voronova.online/health` с
уведомлением в Telegram/email. Это задача надёжности, не блокер текущего API.

### 5. Отдельная миграция PM2-менеджера от root

API-child уже изолирован от root. Перевод самого PM2 и systemd unit на отдельного
пользователя — отдельный высокий инфраструктурный риск: нужна репетиция boot,
monitor и rollback. Не смешивать его с продуктовым релизом.

### 6. CSP для стилей и XSS-регрессия

Script-политика уже строгая. Позже по страницам убрать оставшиеся inline styles,
только затем ужесточать `style-src`. Добавить регулярные XSS-тесты для feedback,
отзывов и payment comments.

### 7. Регулярная гигиена

- раз в месяц: `npm audit --omit=dev`, проверка backup и monitor;
- перед крупными обновлениями: ревизия Node/ОС и maintenance window;
- при масштабировании до нескольких API-процессов: Redis store для rate-limit.

## Не является срочным сейчас

- Sentry/status page — полезны для наблюдаемости, но не закрывают текущий риск;
- Redis не нужен при одном API-процессе;
- миграция inline styles CSP не должна мешать продуктовым задачам;
- не трогать `tmp/threads-og-audit/` в рамках этого плана.
