# Безопасный merge `feature/harvard-plate` в `main`

Дата актуализации: 2026-07-12.

Этот план выполняется строго по одному этапу. После каждого этапа действует контрольная точка: если хотя бы одна проверка не пройдена или результат неоднозначен, следующий этап не начинается.

## Исходное состояние

- Рабочая ветка: `feature/harvard-plate`.
- Зафиксированный HEAD feature: `840d3a227eed9715a5e54bee59e27ab5913f535e`.
- Зафиксированный HEAD `main` и `origin/main`: `d86e4998ba42a8d0be946b0e353ea0f6c4777847`.
- Рабочее дерево чистое, feature совпадает с `origin/feature/harvard-plate`.
- Ветки разошлись сильно: 813 уникальных коммитов feature и 603 уникальных коммита main.
- Сухой merge выявил 12 конфликтных файлов.
- Штатные тесты feature: 22 test files / 194 tests passed.
- `git diff --check main...feature/harvard-plate` пока не чистый: есть trailing whitespace и лишние пустые строки.

## Неподвижные правила безопасности

1. Не выполнять merge непосредственно в рабочей ветке `main` до полной проверки merge-кандидата.
2. Не использовать массово `ours` или `theirs`.
3. Не использовать `reset --hard` и force-push в `main`.
4. Не смешивать Git merge, SQL-миграции и VPS-деплой в одну операцию.
5. `main` — источник истины для актуального публичного сайта и блога; feature — источник истины для `platform/`, `server/` и SmartPlate-ассетов.
6. Минифицированные `main.min.js` и `style.min.css` не разрешать вручную: сначала разрешить исходники, затем пересобрать.
7. Перед каждым переходом сверять фактический commit SHA с записанным ожидаемым SHA.
8. Любая неожиданная модификация рабочих файлов означает остановку и отдельный аудит.

## Этап 1. Зафиксировать исходное состояние

Только чтение: обновить remote refs и повторно снять состояние веток.

```powershell
git fetch origin --prune
git status --short --branch
git rev-parse HEAD
git rev-parse origin/main
git rev-parse origin/feature/harvard-plate
git rev-list --left-right --count origin/main...origin/feature/harvard-plate
git worktree list
```

Проверки этапа:

- рабочее дерево пустое;
- HEAD feature совпадает с `origin/feature/harvard-plate`;
- локальный `main` не используется в другом незавершённом merge;
- SHA записаны в журнал выполнения;
- автообновление блога не изменило `origin/main` между началом и окончанием проверки.

Стоп-условие: любое незакоммиченное изменение, неизвестный worktree или изменившийся SHA требует разбора до продолжения.

## Этап 2. Создать Git-точки отката

Создать отдельные backup-ветки от точных remote SHA и отправить их на `origin`. Названия должны содержать дату и время, чтобы повторный запуск не перезаписал старую точку.

Пример имён:

```text
backup/main-pre-smartplate-20260712-HHMM
backup/feature-pre-merge-20260712-HHMM
```

Проверки этапа:

```powershell
git show-ref --verify refs/heads/<backup-main>
git show-ref --verify refs/heads/<backup-feature>
git ls-remote --heads origin <backup-main> <backup-feature>
git rev-parse <backup-main>
git rev-parse <backup-feature>
```

- backup main должен указывать строго на зафиксированный `origin/main`;
- backup feature должен указывать строго на зафиксированный `origin/feature/harvard-plate`;
- обе ссылки должны существовать на `origin`;
- текущая рабочая ветка и файлы не должны измениться.

Стоп-условие: если remote backup не подтверждён, merge-кандидат не создаётся.

## Этап 3. Зафиксировать рабочее production-состояние

Этот этап ничего не деплоит. Он нужен, чтобы понимать, к чему возвращаться.

Зафиксировать:

- текущий публичный SHA `main`;
- HTTP-статус ключевых страниц `voronova.online`;
- HTTP-статус `plate.voronova.online` и health API;
- статус PM2 и последние ошибки API;
- время и идентификатор последнего успешного backup PostgreSQL.

Перед любыми будущими SQL-изменениями создать отдельный свежий backup БД и подтвердить, что он выгружен в удалённое хранилище. Для самого Git merge восстановление БД не требуется, потому что SQL на этом этапе запрещён.

Проверки этапа:

- публичные страницы отвечают ожидаемым статусом;
- платформа доступна;
- API health успешен и PM2 показывает `online`;
- исходное состояние записано в журнал выполнения;
- при планируемых SQL-изменениях восстановимость backup подтверждена, а не только факт запуска backup-скрипта.

Стоп-условие: если production уже нестабилен, сначала разбирается текущая проблема; merge не используется как способ её исправления.

## Этап 4. Создать изолированный merge-кандидат

Создать новый worktree и ветку от свежего `origin/main`, например:

```text
C:\tmp\smartplate-merge-candidate-20260712
merge/harvard-plate-into-main-20260712
```

В этом worktree выполнить merge с `--no-commit --no-ff`. Основной worktree feature не трогать.

Проверки этапа:

- кандидат создан строго от актуального `origin/main`;
- основной worktree по-прежнему чистый и находится на feature;
- merge ещё не закоммичен;
- список конфликтов сохранён и совпадает с фактическим выводом Git.

Ожидаемые конфликтные файлы:

```text
about.html
blog.html
data/blog-vk-links.json
guides.html
index.html
main.js
main.min.js
scripts/update-blog.js
sitemap.xml
style.css
style.min.css
tests.html
```

Стоп-условие: новый конфликт вне этого списка сначала анализируется и добавляется в план; автоматически продолжать нельзя.

## Этап 5. Разрешить конфликты по группам

Каждая группа разрешается и проверяется отдельно. До завершения всей группы файлы не помечаются resolved.

### 5.1. Блог и автоматизация

Файлы:

- `blog.html`
- `data/blog-vk-links.json`
- `scripts/update-blog.js`

Политика: актуальный контент и публикации брать из `main`. Из feature переносить только доказанно нужную функциональность, которой нет в main. Нельзя заменять весь файл старой feature-версией.

Проверки:

- последние публикации из main сохранились;
- JSON валиден;
- скрипт проходит `node --check`;
- тестовый запуск генератора не удаляет актуальные карточки и ссылки;
- diff не содержит массового неожиданного удаления записей блога.

### 5.2. Публичные HTML-страницы

Файлы:

- `about.html`
- `guides.html`
- `index.html`
- `tests.html`

Политика: использовать свежий main как основу и вручную интегрировать только необходимые SmartPlate-ссылки, разметку или изменения. Старое правило «целиком взять feature для guides.html» больше не применять без повторного сравнения: main продолжал изменяться после появления этого правила.

Проверки:

- нет маркеров конфликтов;
- актуальные тексты, тарифы, FAQ и публичная навигация main сохранены;
- ссылки на SmartPlate ведут на ожидаемый домен;
- HTML открывается локально без видимой поломки header/footer;
- нет неожиданных больших удалений относительно актуального main.

### 5.3. JavaScript публичного сайта

Файлы:

- `main.js`
- `main.min.js`

Политика: вручную разрешить только `main.js`. Затем проверить синтаксис и пересобрать `main.min.js` штатной командой.

Проверки:

```powershell
node --check main.js
npm run build:js
node --check main.min.js
```

- минифицированный файл соответствует пересобранному исходнику;
- ключевые интерактивные элементы публичного сайта работают в preview.

### 5.4. CSS публичного сайта

Файлы:

- `style.css`
- `style.min.css`

Политика: вручную разрешить только `style.css`, сохранив актуальные public-site стили main и добавив необходимые правила feature. Затем пересобрать `style.min.css`.

Проверки:

```powershell
npm run build:css
```

- минифицированный файл пересобран;
- desktop и mobile preview не показывают регрессий header, тарифов, FAQ, блога и guides;
- SmartPlate-связанные публичные элементы отображаются корректно.

### 5.5. Sitemap

Файл: `sitemap.xml`.

Политика: сохранить актуальные URL и даты main, добавить отсутствующие нужные URL feature вручную.

Проверки:

- XML валиден;
- нет дубликатов `<loc>`;
- актуальные страницы main не удалены;
- новые URL действительно существуют и должны индексироваться.

## Этап 6. Полная проверка merge-кандидата до commit

```powershell
git diff --name-only --diff-filter=U
rg -n "^(<<<<<<<|=======|>>>>>>>)" .
git diff --check
npm run build
npm test
```

Дополнительно выполнить `node --check` для изменённых JS-файлов вне тестового покрытия и проверить, что сборка не создала неожиданных изменений.

Проверки этапа:

- нет unresolved-файлов и маркеров конфликтов;
- `git diff --check` завершается с кодом 0;
- build завершается успешно;
- все тесты проходят;
- diff merge-кандидата просмотрен по группам: публичный root, `platform/`, `server/`, SQL, ассеты и документация;
- нет секретов, временных preview-файлов или локальных артефактов, которые не должны попасть в main.

Стоп-условие: любое предупреждение, которое нельзя объяснить, считается неуспешной проверкой.

## Этап 7. Локальный smoke-test merge-кандидата

Запустить локальный сервер из candidate worktree и проверить минимум:

- `/index.html`;
- `/about.html`;
- `/guides.html`;
- `/blog.html`;
- `/tests.html`;
- `/platform/index.html`;
- `/platform/login.html`;
- `/platform/recipe.html` с тестовым рецептом.

Проверить desktop и mobile viewport, навигацию, CSS/JS-загрузку, отсутствие ошибок console и 404 для ключевых ассетов.

Проверки этапа:

- зафиксирован список проверенных URL и результат;
- нет новых console errors;
- нет визуальных регрессий публичного сайта;
- основные гостевые сценарии SmartPlate открываются;
- API-зависимые действия не выполняют необратимых production-изменений.

## Этап 8. Создать и опубликовать merge-коммит кандидата

После успешных этапов 1-7 создать один merge-коммит с двумя родителями. Для максимальной откатываемости не использовать squash: отдельный merge-коммит можно целиком отменить через `git revert -m 1`.

До push ещё раз выполнить:

```powershell
git status --short --branch
npm test
git diff --check HEAD^1..HEAD
git show --stat --oneline HEAD
```

Затем push только candidate-ветки, не `main`.

Проверки этапа:

- commit является merge-коммитом с двумя ожидаемыми родителями;
- первый родитель — зафиксированный main;
- второй родитель — зафиксированная feature;
- candidate-ветка на origin указывает на тот же SHA;
- production не изменился, потому что main ещё не пушился.

## Этап 9. Финальная синхронизация с `origin/main`

Перед выпуском снова выполнить `git fetch origin`. Автоматическое обновление блога могло добавить новые коммиты в main во время подготовки кандидата.

Проверки:

- если `origin/main` не изменился, кандидат остаётся валидным;
- если `origin/main` изменился, в candidate вливается новый `origin/main`, повторно разрешаются конфликты и полностью повторяются этапы 6-8;
- запрещено выпускать кандидат, который не содержит текущий tip `origin/main`.

Стоп-условие: любое изменение main после финальной проверки возвращает процесс к повторной проверке кандидата.

## Этап 10. Контролируемый выпуск в `main`

Только после подтверждения пользователя перевести `main` на проверенный candidate-коммит и push в `origin/main`. Push в main запускает публикацию `voronova.online` через GitHub Pages.

Непосредственно перед push:

```powershell
git rev-parse origin/main
git merge-base --is-ancestor origin/main <candidate-sha>
git status --short --branch
```

Проверки сразу после push:

- `origin/main` указывает на точный candidate SHA;
- GitHub Pages deployment запущен/успешен;
- локальные backup refs и remote backup refs сохранились;
- `platform/` и API на VPS не изменились от одного только push в main.

## Этап 11. Production smoke-test после публикации

Проверить реальные URL без опоры только на локальные файлы:

- главная, about, guides, blog и tests на `voronova.online`;
- загрузку CSS/JS и отсутствие 404;
- актуальность последних публикаций блога;
- ключевые CTA и ссылки на SmartPlate;
- базовую доступность `plate.voronova.online` и API health, чтобы подтвердить отсутствие побочного эффекта.

Проверки выполнять сначала технически по HTTP, затем визуально в браузере desktop/mobile. Зафиксировать время, URL и результат.

Стоп-условие: при критической публичной регрессии не начинать отдельный VPS/SQL-релиз, а сразу переходить к этапу 12.

## Этап 12. Откат при проблеме

Основной безопасный откат опубликованного merge:

```powershell
git checkout main
git pull --ff-only origin main
git revert -m 1 <merge-commit-sha>
git push origin main
```

После revert повторить production smoke-test из этапа 11 и убедиться, что `origin/main` содержит revert-коммит.

Backup-ветки используются как эталон для сравнения и восстановления файлов, но `main` не возвращается через force-push.

Если проблема относится не к GitHub Pages, а к отдельно выполненному позднее VPS-релизу:

1. откатить API-код к отмеченному стабильному SHA;
2. восстановить БД только из проверенного backup, если миграция необратимо изменила данные;
3. вернуть frontend платформы;
4. повторить PM2/API/platform smoke-tests.

## Этап 13. Отдельный релиз платформы, API и SQL

Этот этап не является частью merge в main и начинается отдельным решением после успешного завершения этапа 11.

Перед ним провести аудит: какие `platform/` и `server/` файлы уже находятся на VPS, какие миграции уже применены и какие реально требуют выпуска. Использовать `docs/smartplate-release-checklist.md` и `server/migrate.sh`; не применять весь каталог старых SQL повторно.

Для этого отдельного релиза создаются собственные backup, rollback-план и post-deploy проверки.
